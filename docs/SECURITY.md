# Security and operations rules — LOCAL USE ONLY

What is exposed: a static site built from reviewed files, and a local read-only web app. There is no account, no login, no write route and no API.

- **The public site is static files.** It is built by `python -m live_genesis.snapshot` and holds the chat-app track only. No page carries a script or an inline style; every value is escaped by one helper (`archive_pages.esc`). Each page carries a Content-Security-Policy in a `<meta>` tag (same-origin resources only, no forms, no base URI). `frame-ancestors` works only as a header, so a snapshot on a static host can still be framed. The policy text still allows same-origin scripts and style attributes, left from a removed page; no page uses either.
- **The local web app is not Internet-safe.** `live_genesis.app:app` is for looking at the archive on your own machine: bind it to `127.0.0.1`. It answers GET and HEAD only (anything else: 405), opens the database with SQLite `mode=ro`, never creates or migrates it, has no docs page and no OpenAPI document, and sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY` and the Content-Security-Policy with `frame-ancestors 'none'` on every response. Missing for anything public: TLS, limits shared between processes or surviving a restart, connection and bandwidth limits, monitoring. It also shows the model track, which the owner decided not to publish.
- **Request limit:** one in-memory window per client address (`LIVE_PUBLIC_REQUESTS_PER_MINUTE`, default 300; `/health` exempt), 429 with `Retry-After` beyond it. This process only; reset on restart; at most 10,000 addresses remembered per window and further ones are let through. The address is the direct peer; `X-Forwarded-For` is honoured only when the peer is listed in `LIVE_TRUSTED_PROXIES`.
- **Secrets:** provider keys only in the local `.env` or the shell. Never commit `.env`, a database, `secrets/` or logs. Never print a key; `check-provider` and `archive-check-endpoints` print only whether one is set.
- **Provider keys stay out of the web process:** `.env` is split by `live_genesis/config.py`. Importing the code loads only `LIVE_*` settings. Provider credentials (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_COMPATIBLE_API_KEY`, every key variable named by `LIVE_ARCHIVE_ENDPOINT_<NAME>_KEY_VAR`, and any other non-`LIVE_*` entry) are loaded only by `cli archive-run`, `cli archive-chatbot-ask`, `cli check-provider` and `cli archive-check-endpoints`. The web app deletes those variables from its environment at import and at start-up and imports neither the engine nor a provider SDK (checked by tests). Removing a variable does not scrub the launch-time environment (`/proc/<pid>/environ` still shows it): do not export provider keys in a shell that starts the web app.
- **Endpoints:** a base URL (`LIVE_COMPAT_BASE_URL`, `LIVE_ARCHIVE_ENDPOINT_<NAME>_BASE_URL`) must be `https` unless its host is loopback (`localhost`, 127.0.0.0/8, `::1`) and may carry no credentials or query. It is never written to the database, a plan, an error message, a page or an export; pages show an endpoint's name only. Each call builds its own client from one endpoint's record: its URL, its own key, no retry, **no redirect followed**, so neither a prompt nor a key reaches a host nobody configured. A loopback client ignores proxy settings from the environment. Tested against the real OpenAI SDK on a mock transport; the Anthropic SDK is optional and not installed for the tests, so there only the way the client is built is tested. Prompts sent to a hosted endpoint leave this machine and may be retained by that service; the archive sends only its fixed public questions.
- **Model calls:** two commands call a model: `archive-run` (the model track) and `archive-chatbot-ask` (the chat-app questions put to the model answerers of `archive_chatbots.json`). Each needs the owner's explicit instruction each time, `LIVE_ALLOW_PAID_CALLS=YES` (for local and free models too), a usable key and a required `--max-usd`. Both make every call through one function (`archive._paid_call`: reserve, call, settle, the failure rule), so their gates cannot drift apart. `archive-chatbot-ask --dry-run` calls nothing. Nothing schedules or loops either. Neither contacts a chat app: a model answerer is never an app and may not carry an app's name.
- **Budget:** the ceiling is a local estimate, not a provider limit. Before each call a worst-case amount is reserved atomically, so concurrent runs on one database cannot jointly pass min(`LIVE_SPEND_LIMIT_USD`, `LIVE_PROJECT_BUDGET_USD` − `LIVE_OTHER_COMMITTED_USD`, $1,000 − `LIVE_OTHER_COMMITTED_USD`). Invalid settings fail closed before anything is sent. A call that fails after it may have reached a priced provider stays counted as `unconfirmed` and blocks every paid call until the owner runs `cli reconcile` with the figure from the provider's bill; figures are typed in, never fetched, and can raise the gate but never lower it below the local estimate. A zero-priced endpoint's failed call releases its $0 hold and only that model is skipped. Set a spending limit or alerts at the provider as well. Models can be billed for failed calls.
- **Model and chat-app text is untrusted.** A model never receives another answer. A reply is stored only after the character rule and the content guards; a match is kept as "withheld" with the category and no text. Chat-app replies are typed in by a person from a file and pass the same checks at import; a reply a model gave to `archive-chatbot-ask` passes them before it is stored. For such a model the database and the published file hold the endpoint's name, never its URL, and a provider's error text is never stored, printed or returned: only a reason category.
- **Content guards (heuristic):** `live_genesis/guards.py` matches text that looks like an email address, phone number, Luhn-valid card number, API key or bearer credential, stated password or long secret, payment or donation link, crypto wallet address or checksum-valid IBAN. Invisible, control, private-use and text-direction characters are refused, and removed from older rows when they are read. 62 Cyrillic and Greek letters that look like a Latin letter are folded before matching. A refusal names the category, never the matched text. **Limits:** regular expressions, English and Latin-script centric; they do not understand meaning and can be evaded by spelling a value out or using an unlisted service; names, postal addresses and ID numbers are not detected; false positives exist. They are a floor, not moderation: the owner reads everything before approving it.
- **Publishing recorded data:** a real database is never committed. `snapshot --export` writes exactly `published/archive.json` and `published/MANIFEST.json`, with the chat-app track alone (no model answer, whatever the database holds), and refuses when no hand-entered reply exists, when the block does not fit the checked-in configuration, when a guard matches or when the folder already holds an export and `--replace` was not given. `--check` (what CI runs before every publish) re-checks the hash, that the folder holds exactly those two regular files, ASCII, strict JSON (no NaN, no duplicate key), closed key sets at every level, counts, the guards and `"reviewed": true`; a hand-edited file or manifest is refused, and so is a manifest that says `"contents": "full"` (an export kind that no longer exists). **Only the owner exports and approves**, after reading `archive.json` in full. Once pushed, data stays in git history. Scripted demo answers are never exported; mock and dry-run answers are never exported or rendered.
- **Question locks:** a locked question file is hash-recorded (`archive-lock`, audited); real model answers are refused if the file differs. Append-only tables (answers, runs, locks, the audit log, the chat-app tables) are protected by triggers, which anyone with file access to the database can drop: file access is the trust boundary.
- **Honesty labels:** every page says read-only, whether an answer is a sample or AI-generated and may be wrong, that the site is not affiliated with the app makers, and that there are no payments. Scripted, server-asked, older self-declared and hand-entered answers stay separately labelled in the data.
- **Backups:** `cli backup NEW-FILE` copies are unencrypted and hold everything the database holds. A database made before 14 November 2026 also holds the removed agent society's tables, including agents' private notes and key hashes: treat such a file and its backups as private. Those keys open nothing any more (no route accepts them).
- **Encrypted backups:** `cli backup-encrypted --to DIR` takes the same online copy into a private temporary folder outside every git work tree (folder 0700, file 0600), requires `PRAGMA integrity_check` to say `ok` and `PRAGMA foreign_key_check` to find nothing, encrypts it with GnuPG (an external program, not a Python dependency; symmetric, AES256, passphrase stretched with SHA512 and 65,011,712 iterations, no passphrase caching) into `answers-over-time-<UTC date and time>.sqlite.gpg` in a folder the owner names, and deletes the plain copy in a `finally`, also on Ctrl+C. gpg asks for the passphrase itself: no option, environment variable, file, log line or database row of this project ever holds it, and both gpg calls go through one function (`encrypted_backup._gpg`; its `_passphrase_fd` parameter is for the tests and no command-line option reaches it). Beside the file goes a plain-text receipt: file name, size, sha256 of the encrypted file, time, `user_version`, and the row count of each table (table names and numbers only; no question, no answer). The command refuses a folder inside the project or any git work tree, a missing or unwritable folder, an existing file and a missing database; the audit log gets the file name only. `cli backup-check FILE.gpg` compares the sha256 with the receipt, decrypts a private copy, checks integrity and row counts and deletes the copy; it needs no database and writes to none (`--compare-live` reads the live one with `mode=ro`). **The software makes no network request and holds no cloud credential:** uploading is done by whatever sync program watches the folder. There is no restore command; `docs/BACKUP.md` gives the steps by hand. **Limits:** the backup is only as strong as the passphrase, and a lost passphrase cannot be recovered; the plain copy is deleted, not shredded; the receipt is not encrypted and reveals table names and row counts; nothing checks that the sync program really uploaded the file; the live database itself stays unencrypted.
- **Older databases:** the code never drops or alters a table it does not own. Reading an older database before it was upgraded works (read-only); `cli init` or any other CLI command upgrades the archive tables in place. Back up first.
- **`archive-trends`:** one GET to one fixed https host with a generic User-Agent, a size cap and no redirect to another host; the feed's text is untrusted, stripped of hidden characters and only printed.
- **Other gaps:** no TLS, no WAF, no automatic backups (the encrypted backup is a command the owner runs), no automatic billing reconciliation, no moderation beyond the guards and the owner's review, no monitoring or alerting.
